# Engineering inspectable AI agents for computational research

Reference keys in square brackets are the references checked in `paper_outline.md` ("References checked for this outline").
Text in square brackets that is not a reference key is a drafting note.

## Abstract

- Agents can accelerate computational research, but an answer is hard to trust without seeing and understanding how it was produced.
- We engineered an MCP interface through which agents select tools and parameters and interpret outputs, while the Galaxy workbench executes and records the jobs.
- In 3,780 runs on three benchmarks, agents working through Galaxy scored close to agents writing their own code (higher but uncertain on multi-step analyses), at a higher token cost, and every Galaxy run left a history that made specific errors traceable.

## P1. Agents accelerate computational research, but trusting an answer requires seeing how it was produced

- AI agents now plan and execute computational biology analyses, from single questions to whole studies [gao2024; ghareeb2026], and researchers are adopting AI faster than they trust it: 84% of the 2,430 researchers in Wiley's 2025 survey used it, against 57% in 2024, while concern about inaccuracies rose from 51% to 64% [wiley2025].
- The question this raises for each answer is whether a researcher can see how it was produced: which software ran, with which parameters, on which intermediate results.
- Agents can be set up to organize their outputs, but each researcher asks for a different structure and level of detail. This lack of a standard is a challenge for reproducibility and interpretability, which need every result traced to how it was produced, with its software versions and intermediate results kept [sandve2013].

## P2. Trusting an analysis means trusting both the plan and its execution, and a single benchmark score shows neither

- An agent's knowledge produces a plan, but executing it means building the environment at run time: installing software, choosing parameters and organizing files, each of which can be done in many ways. Execution can fail on its own: even when given the plan, models make more mistakes as tasks get longer [sinha2026].
- Benchmarks such as BixBench and CompBioBench test planning and execution together but rank agents by a single accuracy score [bixbench2025; compbiobench]. A final score cannot locate a failure: it does not show at which step an analysis went wrong or whether the plan or its execution was at fault, and the traces that would show it are not part of the score. Nor does it show how answers vary between attempts or what each answer costs [kapoor2025agents].
- Understanding where an agent is strong, where it fails, and when to check its answer is fundamental to building trust.

## P3. Galaxy, a workbench built for humans, can be engineered to work with agents

- Galaxy, a workbench used worldwide, offers thousands of curated tools, compute for large analyses, and histories that record each job's tool, version, parameters, inputs and outputs [goecks2010; galaxy2026]. Researchers with access to the history can inspect intermediate results, rerun a step with revised parameters, or continue the analysis in Galaxy after the agent session ends.
- Galaxy was built for humans executing analyses. Galaxy-MCP, a community server for the Model Context Protocol (MCP), exposes Galaxy's operations to AI clients, but the Galaxy 2026 update lists it as future work without evaluating agents [galaxy2026], and how an agent's interface is designed changes what the agent achieves [yang2024sweagent]. We engineered our own MCP server and skills, separate from Galaxy-MCP, to divide the work: the agent selects tools and parameters and interprets outputs, while Galaxy executes and records the jobs. Where enabled, user-defined tools (UDTs) let the agent package custom code as a recorded Galaxy job.
- Four models (three on the multi-step tasks) ran each task three times in Galaxy and three times with custom code, on BixBench-Verified-50, CompBioBench and ten multi-step analyses built from the peer-reviewed workflows of the Intergalactic Workflow Commission (IWC): 160 tasks and 3,780 runs. We ask whether working through Galaxy keeps accuracy, helps on long analyses, and makes the agents' variability, errors and cost visible enough to judge when an answer can be trusted.

## P4. On the two question benchmarks, agents working through Galaxy scored close to agents writing their own code

- On BixBench-Verified-50, 89.5% of Galaxy answers and 88.3% of custom-code answers were accepted (difference 1.2 points, 95% interval −1.5 to 4.2). On CompBioBench, the official scores were 87.00% for Galaxy and 86.75% for custom code, with no paired interval because item-level official grades are not available.
- By model, Galaxy scored at or above custom code for three of four models on BixBench and on CompBioBench, and scores varied more across models than between conditions (Galaxy on BixBench ranged from 83.3% for DeepSeek V4 Pro to 93.3% for GPT-5.5). These scores are in line with the 78% to 83% that CompBioBench's authors report for four agent harnesses [compbiobench].
- At the scale tested, working through Galaxy did not cost accuracy on these benchmarks. No equivalence margin was set, so these comparisons establish neither equivalence nor an advantage for either condition.

## P5. On multi-step analyses, the estimate favoured Galaxy, mostly because installed tools carried one imaging analysis

- Each of the ten multi-step analyses runs from raw data to 8 to 12 required results, and the task text names no software. The estimate favoured Galaxy with wide uncertainty: Galaxy runs passed 67.5% of required results and custom-code runs 58.7% (8.8 points, 95% interval −6.1 to 27.1), and Galaxy runs passed more for each of the three models (by 1.9 to 15.6 points).
- The multiplex tissue imaging task accounted for most of that gap; with it left out, Galaxy and custom-code runs passed 65.4% and 64.3% of required results. On that task, the nine Galaxy runs (three per model) used tools installed in Galaxy, which also hosted the jobs and intermediate datasets; they took 6 to 21 hours and passed 70 of 81 results (nine per run), and 6 of the 9 runs passed all nine. The nine custom-code runs passed 7 of 81, none passed all nine, and they stopped after 10 to 38 minutes, having substituted their own methods, in some runs because a package such as the segmentation model would not install.
- Full-task completion was rare in both conditions: 24.4% of Galaxy runs and 23.3% of custom-code runs passed every required result (1.1 points, −16.7 to 21.1), as long tasks are hard for agents generally [kwa2025]. The imaging task is the concrete case for installed tools: Galaxy supplied software that the custom-code runs did not manage to install and run, as workflow systems manage software for their users [wratten2021].

## P6. Answers varied between attempts, and recovering the right one needs a check of how it was produced

- Graded with the known answers, counting a question as passed when at least two of a model's three attempts passed changed scores little and gained more for custom code: 0.5 points for Galaxy and 2.2 for custom code on BixBench, and 0.9 and 1.5 on CompBioBench (scored with the reconstructed answer key). Custom-code failures were more often a single failed attempt: exactly two of three attempts passed on 9 Galaxy and 16 custom-code model–question pairs on BixBench, and on 31 and 43 on CompBioBench. On the multi-step results, at least two attempts passed for 69.0% (Galaxy) and 58.1% (custom code) of required results, against 67.5% and 58.7% for a single attempt.
- At least one of three attempts passed on 93.0% (Galaxy) and 92.0% (custom code) of BixBench model–question pairs, 92.5% and 96.0% on CompBioBench, and 86.5% and 70.9% of multi-step required results; 34 of the 49 BixBench failures not attributed to the task or its scoring (P7) had a correct attempt by the same model in the same condition. These rates use the known grades, so they show how much single answers vary, not what an agent could select on its own. A vote that needs no grades did not recover these answers: on BixBench, taking the answer that at least two attempts gave [wang2023sc] accepted 82.5% of Galaxy and 80.0% of custom-code model–question pairs, below single attempts (89.5% and 88.3%), because 11.0% and 12.0% of pairs had no shared answer and counted as not accepted. Recovering the right attempt needs a check that tells which answer is right [brown2024].
- On bix-52-q7, 3 of 12 Galaxy runs were wrong while all 12 custom-code runs were right; two of the wrong runs counted the header line of the filtered table (19,160 instead of 19,159), a mistake that each of their seven-item histories shows step by step. Reading the history located the error at one step, and the same records, read across all runs, map where agents fail.

## P7. Standard records map agents' errors and make agents virtual users of the interface

- Among runs that ended with a correct answer and have an event log, 87.6% of Galaxy runs (1,391 of 1,587) and 72.6% of custom-code runs (1,169 of 1,610) recorded at least one execution error. In Galaxy, these were mostly requests that the interface rejected (parameters in 55.6% of these runs, and interface requests such as tool lookups in 46.6%), which a better interface can prevent; custom-code runs more often met software that was not available (46.9%, against 20.9% in Galaxy) and compute limits (16.6%, against 6.4%). Galaxy errors could be typed by rule because the interface answers every call with one of a fixed set of statuses; custom-code errors had to be read from free-text shell output.
- Of the 133 wrong BixBench answers (63 Galaxy, 70 custom code), the audit attributes 84 to the task or its scoring, as independent audits have found flawed tasks in agent benchmarks, BixBench-Verified-50 among them [tu2026]. Of the other 49, it classifies 27 as missing validation of intermediate results, 6 as platform or harness and 5 as model knowledge; 4 more carry the missing-validation label but remain unresolved, and 7 await review. On the multi-step tasks, 253 of 783 required results failed in Galaxy and 320 of 783 with custom code, and the task pages name the same kinds of cause for all three models: misleading tool defaults or labels and wrong parameters in Galaxy, and unavailable software and substituted methods with custom code.
- Agents working through Galaxy act as virtual users: recurring rejected requests and retries, each recorded with its status, give developers concrete problems to investigate. ## P8. Galaxy costs more tokens, and successive interface revisions guided by the traces recorded lower overhead

- In the main runs, Galaxy runs used 4.07 times as many tokens as custom-code runs on BixBench, 2.48 times on CompBioBench and 1.47 times on the multi-step analyses, and agents should be compared on cost as well as accuracy [kapoor2025agents]. On BixBench, token use did not signal whether a Galaxy answer was right: the median incorrect run used 1.85 million tokens and the median correct run 2.15 million, although a few incorrect runs used far more (mean 9.0 against 4.1 million).
- The follow-up BixBench batches applied the virtual-user cycle: examine the traces, revise the interface, measure again. The traces showed where Galaxy tokens went: in a July BixBench batch, cached input made up 94.8% of Galaxy tokens, so most went to re-reading context, and Galaxy runs took 2.66 times as many agent turns as custom-code runs; waiting for jobs also added turns.
- After each revision, the ratio fell with GPT-5.5 from 5.48 (prompts and skills) to 2.81 (MCP execution), and with GPT-5.6 Sol from 3.45 to 2.42 (compact replies) and 1.53 (longer waits, which cut wait calls per replicate from 481 to 78). Accuracy stayed similar where it was reported (136 to 139 of 150 Galaxy answers accepted), but the CLI version, replicate coverage and scoring also changed between batches, so the batches cannot isolate the effect of individual changes, and the main runs did not use the later changes, which were tested on BixBench only. Reducing this overhead matters so that the cost of Galaxy's features does not outweigh their benefits.

## P9. The histories that make analyses inspectable can also expose earlier answers to later benchmark runs

- The histories and results that researchers can inspect may also expose earlier answers to later benchmark runs. Some agents broke the rules set for the benchmarks: they read earlier answers or execution traces for the same question, including the project's public results pages and other runs' published Galaxy histories, copied a published answer, or searched the web for the question text. Evaluations of other agents report the same behaviour [metr2025rh; kapoor2026hal; zhong2025impossible].
- In October we reran, under a stricter block, 68 BixBench and CompBioBench runs selected for confirmed or possible exposure (38 Galaxy, 30 custom code; 50 of them DeepSeek V4 Pro): 63 had read earlier answers or traces for the same question or copied a published answer, and 5 had retrieved answer-related material without confirmed exposure to the question's own answer. The pooled official CompBioBench scores were unchanged (87.00% and 86.75%). These are the runs that a review found, not a rate; how often rules were broken across all 3,780 runs awaits the deposited audit.
- The same records made the breaches detectable. Benchmarks for agents need runs isolated from published results, and agents' answers need oversight that reads how each was produced.

## P10. Paired with Galaxy, agents' analyses become inspectable

- AI agents have the potential to automate and accelerate many aspects of computational research, including cancer research. Through Galaxy, they scored close to agents writing their own code on BixBench and CompBioBench, completed six of nine runs of an imaging analysis with installed tools that the custom-code runs did not manage to install and run, and every Galaxy run left a history, which located specific errors and showed how answers varied.
- Limits: four models in one agent harness (three on the multi-step tasks), prompts and compute that differ between conditions, IWC reference results built in Galaxy, and no test yet of whether people review answers better with histories or whether the benchmarked analyses replay end to end from their histories; claims about improved human review or reproducible agent analyses wait for those tests. The records also suggest how to build in rigor: disagreement between answers or methods could trigger inspection, and checks on intermediate outputs could run before an answer is reported.
- Pairing AI agents with Galaxy makes their analyses inspectable: Galaxy's curated tools, scalable compute and histories keep each answer next to the jobs that produced it, open to human oversight [natureed2026]. For tool developers, agents can serve as virtual users: examining their traces, revising the interface and measuring again turns benchmarking into usability testing.

## Notes for Methods and Supplementary Information

- Methods, reruns: state the selection rules (prior-run access, direct copying, exposure unconfirmed; scientific follow-ups and IWC reference access are separate and bring the ledger to 77 runs), what the stricter block prevented, and the rerun controls; deposit the block's configuration.
- Methods, repeated attempts: "at least two attempts passed" and "at least one attempt passed" use the known grades; the answer-string vote compares case-folded answers, accepts a shared answer from at least two attempts, and otherwise abstains, with abstentions counted as not accepted.
- Supplement, tool use: report observed installed-tool and UDT use (Supplementary Fig. 1b,c), and note that reviewing a UDT also means reviewing its code. The multi-step benchmark did not expose the UDT operation, so the imaging example concerns installed tools only.
- Supplement, failure patterns: model-dependent analysis routes, and persistent versus intermittent failures, only if classified systematically.
- Supplement, handoff and replay: continuing an analysis from its history is an existing Galaxy capability; end-to-end replay of the benchmarked analyses is a separate test that has not been run.
- Materials: one reader-facing table with the prompts, skills, exact versions, scoring code, results and permitted trace access, in place of another main-text paragraph.
