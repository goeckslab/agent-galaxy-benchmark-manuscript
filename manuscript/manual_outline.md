# Engineering a Galaxy interface for trustworthy biological computational analyses with AI agents

## Abstract
AI agents can accelerate data analysis, yet trusting their performance requires accurate results that researchers can validate. Here we describe an agent interface to the Galaxy workbench through which agents plan analyses while Galaxy executes and records each job. On three biological benchmarks, agents using Galaxy scored close to agents writing and executing their own code. We demonstrate how Galaxy features can be used to increase human-interpretable insights and trust on agents.

## P1. Agents can speed up computational analyses but are not fully trusted
AI agents now plan and execute computational biology analyses, from simple tasks to whole complex studies [REF]. However, researchers are adopting AI faster than they trust it. Agent benchmarks do little to close this gap. The scores are used as a reference of agents capability, representing model's accuracy, which is evaluated by the number of correct answers returned for given tasks. But a high-quality analysis must also be reproducible, buit from validated tools, consistent with community best practice, run at the scale the data demand, and open to inspection by the researchers who rely on it. 

# P2. What agents lack to increase trust; how to bridge the gap
An agent byitself rarely meets these requirements by default. Each run assembles a disposable enviroment on a single machine, installs software versions it finds suitable, and produces artifacts without following specific standard to generate them. As consequence, once the sandbox is gone the result cannot be rerun. The analysis exists only as code that programmers can audit, it is limited to the memory and cores of one machine, and its errors accumulate as tasks get longer. Galaxy, a research workbench built for people over two decades, already meets each of these requirements [REF]. It is accessible, reproducible, and scalable. Furthermore, tools are curated and it encodes best practice. And crucially, Galaxy keeps the same record whether a person or a program submits the job.

# P3. This work
Galaxy therefore offers agents what they lack, and offers researchers a way to check, rerun and reuse what agents produce. A community server, Galaxy-MCP, exposes Galaxy's operations to agents through the Model Context Protocol (MCP), an open standard already used to turn published scientific software into agent tools [REF]. What remains untested is whether agents stay accurate when they work through a curated platform. Restricting an agent to curated tools could cost accuracy, by removing the freedom to write bespoke code, or improve it, by replacing improvised pipelines with validated ones. Because the design of an agent's interface shapes what the agent achieves [REF], we built our own MCP server and agent skills, through which agents plan analyses and choose tools while Galaxy executes and records each job. We compared four models working through Galaxy with the same models writing their own code on BixBench-Verified-50 [REF], CompBioBench [REF] and ten multi-step analyses built from IWC workflows [REF], running each task three times per condition (3,780 runs; three models on the multi-step tasks). Every Galaxy run leaves a history that a researcher can open, inspect and rerun, so agents and the people who rely on them work in the same workbench.

# P4. Agents working through Galaxy to solve direct biological tasks scored close to agents writing their own code

To test whether working through Galaxy costs agents accuracy, four models (GPT-5.5, GPT-5.6 Sol, GPT-5.6 Luna and DeepSeek V4 Pro) answered questions of two public available benchmarks [REF] three times in each of two conditions; custom code condition is when agents write and run their own code in its local environment, Galaxy condition is when agents change the execution to the workbench. On BixBench, where each answer is graded individually, 88.3% of custom code answers and 89.5% of Galaxy answers were accepted (600 runs per condition; paired difference 1.2 points, 95% interval -1.5 to 4.2; Fig. 1a). On CompBioBench, which returns only an official total per submission, custom code and Galaxy scored 87% and 87% (mean of three submissions per model; Fig. 1b), and no model differed by more than 1.3 points between conditions. All these scores were above the 78% to 83% that the benchmark's authors reported for other agent conditions [REF]. These results do not show that Galaxy makes agents more accurate, but they remove accuracy as a reason to prefer custom code. 

# P5. On multi-step analyses, lower-scoring models passed more required results in Galaxy, much of it on one imaging task

The two public benchmarks grade a final answer, so they cannot show whether an agent keeps a long analysis on course. We therefore built a third benchmark from ten workflows peer-reviewed by the IWC [REF]. Each task gives the agent raw data and an analysis goal and grades 8-12 required results produced along the way, so a run scores well only if its pipeline stays aligned with the reviewed workflow at every stage. Across the three models, Galaxy runs passed 67.5% of required results and custom-code runs 58.7%, a difference of 8.8 points whose 95% interval (−6.1 to 27.1) includes zero, because most of the gain came from one multiplex imaging task. The strongest model, GPT-5.6 Sol, passed a similar share of required results in both conditions (88.0% with custom code against 89.9% in Galaxy; 30 runs per condition), whereas the two lower-scoring models passed more in Galaxy (GPT-5.6 Luna 33.9% against 49.5%, and DeepSeek V4 Pro 54.3% against 63.1%; Fig 1b). Without the imaging task, GPT-5.6 Luna kept its gain (37.7% with custom code against 47.2% in Galaxy), DeepSeek V4 Pro did not (60.4% against 60.2%), and GPT-5.6 Sol passed fewer required results in Galaxy (94.8% against 88.8%).

# P6. Custom code and Galaxy failed for different reasons, and Galaxy's failures were less often repeated and easier to inspect

The two conditions also failed for different reasons. On the IWC benchmark, the per-task error analyses most often blamed custom-code failures on agents replacing the specified tools with their own code, sometimes after the software failed to install. The imaging task showed the cost of this substitution: custom-code runs passed 7 of its 81 required results, whereas Galaxy runs, using the pipeline's installed tools, passed 70. In Galaxy, the analyses most often named how the tools were set instead: parameter choices, including misleading tool defaults. On BixBench, we traced 45 wrong answers through their run logs and found knowledge or execution errors. Knowledge errors, in which the agent chose the wrong analysis, were about as frequent in both conditions (12 in Galaxy, 15 with custom code), whereas execution errors, in which a correct analysis was carried out wrongly, were twice as frequent in Galaxy (12 in Galaxy, 6 with custom code). Half of these Galaxy errors were data-handling slips, such as a filtered table that kept its header line and gave 19,160 rows instead of 19,159, and 7 of the 12 can be seen in the run's history, whereas custom-code slips stay inside scripts. Galaxy results are therefore easier to trust, because their errors are easier to find and to correct because each step is recorded in a history where a researcher can spot a slip, and fewer Galaxy results failed in all three attempts (34 of 261 required results, against 74 of 261 with custom code), so repeating the analysis more often produced the correct result. The same records let agents serve as virtual users of Galaxy, whose failures point to gaps and issues in its tools and interface, such as a tool form whose preset gene count overrode the requested selection cutoffs, or a filtering tool that agents searched for and could not find on usegalaxy.org. Researchers use the same forms and tools, so fixing what agents expose could improve Galaxy for both.

# P7. Repeated attempts often included a correct answer that a majority vote missed, so each answer needs validation

Repeating an analysis helps only if the correct attempt can be recognized. A correct answer was often among the three attempts. At least one attempt passed for 93.0% of Galaxy and 92.0% of custom-code BixBench model–question pairs, for 86.5% of Galaxy and 70.9% of custom-code multi-step required results, and, on CompBioBench scored with a reconstructed answer key, for 92.5% and 96.0%. Of the 45 traced BixBench errors, 34 came from a model that answered correctly in another attempt. A majority vote recovered only part of this potential: counting a result as passed when at least two of three attempts passed changed scores by at most 2.2 points, because a lone correct attempt was outvoted, as in 46 Galaxy and 35 custom-code multi-step results. Agreement between attempts is therefore no substitute for validation; each answer must be checked against how it was produced. Galaxy histories make this check feasible, because attempts that disagree can be compared step by step to find where they diverged. Agents could also run different methods for the same step, or test intermediate results before reporting, approaches we did not test here.

## Token use was higher with Galaxy and lower in successive interface development batches

- In the main runs, Galaxy runs used 4.07 times as many tokens as custom-code runs on BixBench, 2.48 times on CompBioBench and 1.47 times on the multi-step analyses, and agents should be compared on cost as well as accuracy. On BixBench, token use did not signal whether a Galaxy answer was right: the median incorrect run used 1.85 million tokens and the median correct run 2.15 million, although a few incorrect runs used far more (mean 9.0 against 4.1 million).
- Development batches on BixBench followed the virtual-user cycle: examine the traces, revise the interface, measure again.
- Across batches, the observed Galaxy-to-custom-code token ratio was lowering as we better engineered the interface: with GPT-5.5, 5.48 (prompts and skills) and then 2.81 (MCP execution); with GPT-5.6 Sol, 3.45, then 2.42 (compact replies) and 1.53 (longer waits). Galaxy accuracy was held, the number of tasks accepted was of 136 to 139 of 150 answers correct. The main runs did not use the later changes, which were tested on BixBench only, and reducing this overhead matters so that the cost of Galaxy's features does not outweigh their benefits.

## Galaxy kept scores close and helped the lower-scoring models on long analyses; the models, tasks and harness limit how far this generalizes

- Across three benchmarks, agents working through Galaxy scored close to agents writing their own code on BixBench and CompBioBench, and the lower-scoring models passed more multi-step results in Galaxy. The errors that prevented correct answers were mostly analytical choices and slips in steps that ran to completion, not rejected requests, and answers varied between attempts in both conditions, so each answer needs a check of how it was produced.
- The four models were run between July and October 2026 in one agent harness (three models on the multi-step tasks), and newer models have been released since, as the field moves fast. Because the strongest model scored high in both conditions and the lower-scoring models gained more from Galaxy, the pattern across models, rather than any one model's score, is what can guide how newer models are used with Galaxy.
- The tasks do not cover every method important to computational research: BixBench and CompBioBench ask single questions, and the ten multi-step tasks span ten analyses from genome assembly to tissue imaging. They are enough to show how agents use Galaxy's tools, where they fail and what their records reveal. Other limits: CompBioBench has no audit of failure causes; the error classifications await a second reader; we did not test whether people review answers better with histories; and 68 BixBench and CompBioBench runs with confirmed or possible exposure to earlier published answers were rerun under a stricter block (Methods), leaving the pooled official CompBioBench scores unchanged (87.00% and 86.75%).

## Executed in Galaxy, an agent's analysis inherits the workbench's reproducibility, scale and curated tools, and stays open to human review

- Working inside Galaxy, an agent uses features built for human researchers: curated, versioned tools maintained by the community, including the IWC's peer-reviewed workflows as best practice; compute that scales to large analyses, such as the 6- to 21-hour imaging runs; access to software without installing it; and histories that record each job's tool, version, parameters, inputs and outputs, so that the analysis can be rerun. Its results come from tools the community maintains and tests, not from code written anew in each run.
- Galaxy's interface brings people into the evaluation. A researcher can open the agent's history, inspect each intermediate result, find mistakes such as the header line counted in bix-52-q7, rerun a step with revised parameters and validate the final answer. Every one of the 1,890 Galaxy runs has a history link, and histories can be shared and published with a link, so collaborators and reviewers see the same analysis.
- Pairing agents with Galaxy divides the work: the agent plans and chooses tools, Galaxy executes and records, and a person reviews. This moves agent-driven research from answers that must be taken on trust toward analyses that can be inspected, reproduced and shared.
